# 评测用例

这个目录回答一个问题：**用户说一句话，检索有没有把对的那张卡排上来。** 不是「能不能搜到字」，是「排第一的是不是该排第一的」。

## 两条赛道

| 目录 | 是什么 | 门槛 | 用来挡什么 |
| --- | --- | --- | --- |
| `cases/<scene>.jsonl` | 用户真实会打出来的话，通常带着卡里出现过的词 | 严格（hit@1 95%） | 排序退化、加卡把好结果挤下去 |
| `paraphrase/<scene>.jsonl` | 同一种处境换个说法，刻意避开卡里的关键词 | 宽松（hit@1 75%） | 检索只会背原词、换句话就找不到 |
| `offtopic.txt` | 12 条明显无关的句子 | 不进门槛 | 假阳性：无关的话也能拿到高分 |

改写赛道是这两条里更有用的那条。直接问法很容易被「加几个同义词」刷上去，改写问法刷不动，因为它考的是语义相近而不是字面相近。

## 用例格式

一行一个 JSON，三个字段：

```json
{"query": "她说腰跟断了似的，坐一会儿就得站起来", "scene": "period", "expect": ["period-004"]}
```

- `query`：用户会打出来的那句话，口语，可以带情绪，别写成标签堆砌（「痛经 腰酸 躺着」这种写法会让人误以为检索很准）。
- `scene`：十个场景之一。评测时按场景检索，所以 `scene` 也参与 `route@1` 的统计。
- `expect`：**应该排在前面的卡 id**，可以多张。命中 `expect` 里任意一张算 hit@3，排第 0 位算 hit@1。写两张是允许的，说明这两种都算对。

## 门槛

`gate.json` 里每个数字都是「跌破就红」的意思：

```json
{"min_hit1": 0.95, "min_hit3": 0.98, "min_mrr": 0.95, "min_route": 0.95,
 "scene_min_hit3": 0.90,
 "para_min_hit1": 0.75, "para_min_hit3": 0.90, "para_min_mrr": 0.80,
 "para_min_route": 0.90, "para_scene_min_hit3": 0.60}
```

`scene_min_hit3` 按场景单独算，任何一个场景掉下去就红。这条是核心：整体 95% 可以由九个场景满分加一个场景 50% 凑出来，按场景卡就凑不出来。

## 三条口径

1. **用例写「处境」，不写「关键词」。** 「她说疼得坐着都难受」是好用例；「肚子疼 痛经」不是，后者测的是分词器，不是检索。
2. **expect 对准卡，不对准场景。** 只写 `scene` 的话，检索把八竿子打不着的卡排第一也照样算对。
3. **改门槛要有理由。** 把 hit@1 从 95% 降到 90%，等于对外承诺「二十次里错一次」。PR 里写清为什么这 5% 换得回别的东西。

## 怎么跑

```bash
python scripts/eval.py            # 两条赛道，逐场景报告，掉线退出 1
python scripts/eval.py -v         # 多打印每条的排名，找 miss 用
python scripts/eval.py --calibrate # 相关与无关的分数分布
```

`--calibrate` 的输出用来判断「一张卡分数低到什么程度可以认为是没找到」。`scripts/index.py` 里的 `WEAK_SCORE` 就是照它定的：相关句子的 top1 最低 44 分，无关句子最高 21.6 分，取 20 作提示线，中间留出余量。

## 加用例之前

先跑一遍你现在想加的这句话：

```bash
python scripts/query.py --explain "你要加的那句" --scene <场景>
```

如果它命中的卡明显不对，那是**加用例的时机**，先记下来再改检索。如果它已经命中得挺好，说明这条不需要新用例，加了只是让分数好看。
